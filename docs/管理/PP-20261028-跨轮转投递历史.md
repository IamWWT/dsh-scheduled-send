# 跨轮转的投递/执行历史（0.10.9）

目标：per-run 任务（每次执行新建会话）在任务页能看到**跨轮转、跨重启**的投递与执行记录；
`fixed` 任务同样有一份「官方投递历史 + 执行结果」合一视图。

## 需求（用户诉求）

> 「历史上哪次投递进了哪个会话、那次执行成功还是失败，轮转完就查不到了。」（0.10.8 已知取舍的补齐）

0.10.8 的取舍原文见 [每次执行新建会话](PP-20261028-每次执行新建会话.md)「已知取舍」：
per-run 轮转 = `create(新会话)` + `delete(旧任务)`，官方 `history()` 对新任务是空。
官方没有「改绑定」的公开面，所以不能靠保留任务行保住历史 —— 只能在插件侧自持等价记录。

## 官方契约核对（决定实现方式）

- `history(request)` 只按「当前任务行」查会话收件箱回执（`ScheduleDeliveryHistoryRequest{ sessionId, id }`），
  旧任务行删除后其历史不可达；插件不去伪造/补写官方存储。
- 投递回执的可观察面 = `catalog()` 每行的 `lastDelivery{ scheduledAt, deliveredAt, messageId }`，
  投递提交后官方 `emitChanged()` → 插件 `schedule/changed` 触发刷新（页面关闭也生效）。
  ⇒ 插件以 `messageId` 为幂等键，用「刷新时比对」而不是「事件里猜」。
- 执行结果的可观察面 = 会话事件 `user/message(source.kind='schedule')` framing 里的
  `schedule_id_json` + `turn/end` 的 `reason.kind`（0.8.x 起既有链路）。

## 语义

1. **聚合键**：`taskKey`（`tasks-meta.json` 的 `tasks.<官方 id>.taskKey`）。创建时分配，per-run 轮转
   （`carriedMeta`）、半截交换收尾（`completePendingSwaps`）、暂停/恢复、归档迁移、恢复默认
   （`carryTaskKey`）都继承。官方 task id 由服务端分配、轮转必变，绝不能当聚合键。
2. **记一次投递**：`recordDeliveries()` 在 `doRefresh()` 里、`rotatePerRun()` **之前**执行 ——
   轮转后旧任务行已删，投递回执与「接收它的会话」就没了。记录 `sessionId` = 该任务当时的绑定会话，
   `sessionTitle` = 当时的会话标题快照（轮转不会把历史行的标题改掉）。
3. **记一次手动执行**：`runNow()` 在 `prompt()` 成功后写一条 `reason='manual-run'`，
   `messageId='manual:<requestId>'`（没有官方回执，用请求 id 当幂等键），同样在轮转之前。
4. **吸附执行结果**：`turn/end` 里 `attachExecution(taskKey, sessionId, record)` 找**同会话最早一条还没有
   结果**的记录写入（FIFO：投递先排队、轮次后依次结束）。per-run 轮转后事件里的旧 task id 已从元数据
   删除，靠 `rotatedTo` 映射找回同一个任务键（`taskKeyOf()`）；找不到就只告警不新建条目 ——
   历史以「投递」为准，避免同一次投递出现两条。
   - **手动执行**走普通 `prompt`，没有 schedule framing：`runNow()` 登记「这个会话刚发起手动请求」，
     该会话下一个非 framing 的 `turn/end` 归给它（`finishManualRun()`），所以手动执行也有执行状态。
   - **顺序兜底**：隔离实测发现模型快速失败（30–130ms）时 `turn/end` 可能早于「刷新读到投递回执」，
     于是执行结果先进 10 分钟缓冲（`orphanExecutions`），投递记录一落地就补吸附（`drainOrphanExecution()`）；
     不这样做那条记录会永远停在「投递成功」。
5. **幂等**：`appendRun()` 先按 `messageId` 判重。刷新极其频繁（UI 5s 轮询 + `schedule/changed`），
   不幂等就会每秒写一条。
6. **上限与截断**：每任务 200 条，超出丢最旧并累加 `dropped`；`TaskView.historyTruncated` 与面板都说明
   已截断（用户明确要求「在 UI 说明已截断」）。
7. **失败不连坐**：所有历史写入走 `safeHistory()`；`MetaStore.save()` 本身也只 `console.warn`。
   写盘失败时投递/轮转照常完成，页面仍能读到内存里的历史（测试 7 用「把 meta 文件换成目录」实证）。
8. **收敛**：任务被删除/清理已结束后，`pruneHistories(liveTaskKeys())` 丢掉无主历史；
   暂停中的预置任务（官方行已删、快照还在）算「活着」，恢复后历史不断。

## 顺手修掉的两处既有偏差（0.10.9 实测暴露）

1. **执行状态写回旧 id**：`turn/end` 里 `meta.set(id, …)` 会为已被轮转删除的旧 id 重新建一行（无主元数据，
   且带一个新任务键）。改为先按 `rotatedTo` 把 id 归一到当前任务（`metaIdFor()`）再写，历史吸附也随之正确。
2. **元数据对账时刻**：`reconcile` 的 `snapshotAt` 原本取在**读官方目录之后**，于是同一次刷新里并发写入的
   元数据（`create()` 刚写的 `builtin`/`sessionMode`）被当成「官方已删」清掉（隔离实测约 1/6 概率丢
   `builtin`，归档迁移后就丢了预置归属）。改为在 `doRefresh()` 入口取时刻。

## 为什么不动调度语义

投递、重复规则、补投、持久化全部仍由 `ctx.schedule` 负责；本版只增加**只读观察 + 元数据落盘**。
唯一碰到任务行的改动是 0.8.x 起既有的轮转路径，且只在它前后插入记录调用，不改判定与顺序。
